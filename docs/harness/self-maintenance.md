# AGENTS 与 Harness 自维护协议

## 原则

AI 是规则的主要维护者，但规则修改必须可追溯、可验证，并且不能为当前任务自我降级。

## 自动维护触发器

AI 应主动提出或直接同步：

- 引用路径、命令或模块已经变化；
- 同一错误重复出现；
- 规则与代码、ADR、里程碑或 CI 冲突；
- 根规则过于具体，应下沉局部目录；
- 多份文件重复表达同一规则；
- 某个目录形成至少三条稳定的局部约束；
- 文本规则已经完全由机器检查替代；
- 现有门禁不能发现一次真实事故或高风险缺口。

安全、数据破坏和跨作用域泄漏一次真实事故即可触发，不要求重复。

## 维护级别

### 机械同步

路径、命令、索引、拼写等不改变语义的修改，可以随导致事实变化的 PR 一起完成。

### 规则语义变化

新增、删除、提升、下沉或改变规则含义，按至少 R2 的治理变更处理。

### 治理根变化

放宽红线、修改自动合并、安全、隐私、质量门、发布权限或自主等级，按 R3 处理。

## 当前任务不得自我豁免

- 任务开始时读取到的规则约束整个任务。
- 本任务修改的 `AGENTS.md` 或 Harness 只对后续独立任务生效。
- 如果实现与旧规则冲突，先按旧规则完成或将规则变化拆成治理 PR。
- 不得先删除检查，再提交原本会失败的实现。

## 作用域选择

规则放在能完整覆盖问题的最深目录：

- 只影响 SQLite 迁移的规则放在 `packages/memory-store/AGENTS.md`；
- 只影响 Runtime 规范化的规则放在 `packages/pi-adapter/AGENTS.md`；
- 全仓才适用的红线才放根 `AGENTS.md`。

父级文件只链接，不复制局部规则正文。

## 规则质量标准

每条长期规则应当：

- 有明确适用范围；
- 能判断是否违反；
- 有验证方法或失败信号；
- 不重复其他事实源；
- 不依赖临时文件名或一次性实现细节；
- 说明“必须做什么”，而非空泛地要求高质量。

## 治理 PR 说明

治理 PR 至少说明：

- 触发原因和证据；
- 旧规则与新规则；
- 为什么选择这个作用域；
- 是否改变权限或质量门；
- 机器检查如何同步；
- 影响和回滚；
- 独立 AI 审查结果。

## 定期审计

AI 可在以下时机运行治理审计：

- 每个里程碑开始和结束；
- 大型目录重构后；
- 连续出现两个规则相关返工后；
- CI/Harness 发生事故后；
- 根 `AGENTS.md` 接近信息预算上限时。

审计应优先删除重复、修复漂移和增强机器检查，不以增加规则数量为目标。
