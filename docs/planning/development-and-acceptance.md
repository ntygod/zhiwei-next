# 开发实现与产品验收分离

## 决策、范围与生效

治理 [#108](https://github.com/ntygod/zhiwei-next/issues/108) 承接所有者明确分工：“你来承担开发，测试验证那些我可以以后做”，以及继续自主开发的指令。AI 负责代码实现、必要的开发验证与交付；用户可以随后做产品体验与正式场景验收。用户稍后验收不意味着 AI 可以跳过类型检查、不变量测试、真实存储开发测试、CI 或独立审查。

本次只调整实现顺序与状态表达，不改变产品、安全或授权保证，不实现产品代码。当前治理 PR 仍受开始时旧规则约束；完整原检查、当前 HEAD 独立 R3、当前 PR Runtime 来源、Ready CI、受保护合入与 main provenance 全部保持。新模式仅在本治理合入后对下一独立任务生效。

## 唯一事实源与两个依赖用途

- `development-plan.json` v2 仍是唯一任务内容、场景、合同、风险、退出门及**产品验收/启用依赖**事实源。原 `depends` DAG 原样保留；它不再作为每一行代码的开工前置。
- [execution-mode.json](execution-mode.json) v1 只引用原任务 ID，记录合成开发的 `implementation_depends`、`implementation_status`、`acceptance_status` 和证据链接，不复制任务正文。未列入的 P2—P5/条件任务继续按原依赖，不凭本模式提前实施。
- `implementation-plan.md` 是原任务目录的生成视图；本文件是开发/验收分工的唯一语义来源。项目状态/交接只保存当前工作摘要，不能覆盖机器索引。
- `implementation_status` 为 `not_started / in_progress / implemented / blocked`；`implemented` 只表示该任务已交付的代码范围与开发验证，有精确 PR/commit 证据，不能当作产品可用。
- `acceptance_status` 为 `not_run / pending / passed / failed / blocked`；本索引记录产品/真实场景验收，组件单测不会将它自动改为 `passed`。验收通过还须原依赖、逐项真实证据和实际授权；索引检查本身不认证远端证据或授予权限。非初始状态附证据或阻塞引用；`blocked` 的链接说明限制，绝不是成功证据。

P0-03 与 P0-04 已分别由 PR103、PR107 保护合入，代码实现为 `implemented`。相关 Z03/Z16、Z14/Z15 产品场景仍 `not_run`，不是否认组件测试已通过。P0-01 受原安全实验执行限制保持 `blocked`，P0-02 产品验收也被原前置阻塞；D-04/D-08 仍 Proposed，G-2/G-5 未通过。本模式不运行、重演或替代受限实验，不更换环境绕过限制。

## 合成开发的实际边界

允许按技术依赖在正式 `packages/domain`、`cognition-core`、`protocol`、`memory-store` 与后续服务实现路径编写产品代码，使用合成输入、隔离临时测试资源、显式注入的模型/I/O 边界。无需为了每个纯函数重新增设 P0 准备任务。

合成不是降低完整性标准：存储实现必须使用真实临时数据库验证事务/迁移/恢复，不能用 Mock SQL 代替；纯领域依旧无 I/O；服务集成测试须标明受控假实现与尚未验证的真实能力。正常类型、单元、集成及负例测试均由 AI 执行，平台明确禁止的实验除外，无法验证如实记 `not_run/blocked`。不得把合成成功宣称为真实授权、Provider 支持或产品安全。

代码提交/合入与运行启用分开。未验收实现只能由合成测试入口调用，或保持默认关闭且拒绝真实调用的接线；不得把一个 `authorized: true`、`accepted: true` 或人工置位字段当作安全证明。此治理不创建通用绕过开关。任何正式入口启用需另列检查证据，并仍受原 task DAG/阶段门约束。

真实个人数据读取/迁移、实际模型请求或外发、凭据接入、部署/发布和真实外部副作用均未获本模式许可；必须另行满足具体授权、平台约束和原接入验收门。既有诊断/Runtime 取证流程按原合同运行，不由本模式扩大。

## 真实技术依赖与下一实现

下一唯一实现是 **P1-01 建立认知与任务领域合同**，不是新的 P0 准备卡：

- 复用已交付 P0-03 Task/Attempt/Outcome；保留其内存计算与持久 CAS 的区分。
- 正式 Scope、privacy、sourceTrust、epistemic、认知对象/版本关系与错误合同；Observation v2 和 Local API DTO 用独立版本与序列化 Fixture，不修改 v1。
- 只触及该任务原有 domain/cognition-core/protocol 路径；合成输入、显式时间/ID、确定性校验/转换。无生产消费者、模型、数据库迁移或服务启用。
- 验证正反例、Scope 不漂移、模型推断不直接取得事实或权限、纠正保留历史、未知/失败不伪成完成、v1 兼容与完整类型检查。未执行的跨会话/真实存储/运行权限场景继续留待对应任务验收。

P1-01 的实际实现依赖为 P0-03；预算选择与领域合同无计算依赖，P0-04 保持为 P1-06 的真实消费者前置。P1-02 需要 P1-01 正式版本合同；P1-03—09 继续沿现有技术链递进。P0-02 的合成基准/夹具代码无需安全实验结果即可编写，但它不能完成 G-5 验收或证明 P0 已退出。

本模式没有宣布所有技术依赖已消失；若前置合同/公开接口尚不存在，应先完成前置实现，不用空壳、复制内部代码或伪造证据绕过。任务过大可以按同一 P1 用户结果拆交付切片，后续切片仍由一个 canonical work item/primary PR 规则管理，不恢复 P0 准备卡循环。

## 校验、威胁与回滚

原 design-plan `validate()`、10 个负例、完整前阶段验收 DAG 和旧计划 SHA 检查保持；仅生成文字将“先依赖再实施”机械同步为验收启用用途。新 `check:execution-mode` 增量验证引用、双状态、技术 DAG、证据结构、无环与未满足原验收依赖不得记通过，并拒绝未知启用字段。它不执行安全实验、不读凭据、不查询真实用户数据、不伪装远端批准。

重点反例：把 `implemented` 当 `passed`；移除真实技术依赖；用新模式设 activation 标志；以合成证据扩大许可；声称 P0 退出；用此治理的新增规则给自身产品实现放行。均必须拒绝或保持产品入口关闭。

回滚通过新的受审 PR revert 本治理，恢复旧选工解释；原任务目录、历史实证、已有组件与保护链不删除。本项没有数据库或权限副作用，正反补丁演练须能恢复精确树。若后续已有合入实现，不删除其真实交付记录；先停止未验收入口并按相应任务恢复合同处置。
