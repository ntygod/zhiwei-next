# 纯领域实现准备与正式接入边界

## 决策与生效

规划 work item [#100](https://github.com/ntygod/zhiwei-next/issues/100)承接所有者在 [PR99](https://github.com/ntygod/zhiwei-next/pull/99#issuecomment-6092299142)停止视觉打磨、优先核心开发及随后明确继续自主推进的方向。原 P0 安全与存储前置仍是正式接入所需证据；纯内存领域计算不读取这些环境，也不需要把它们伪标完成。

本规划按旧规则独立 R3 审查、CI 与保护合入后，才对后续独立实现任务生效。本 PR 不实现 P0-03，不把尚未获得的审查写成批准。它是工作拆分记录，不变更 ADR0016—0018 的产品、权限、存储或 Runtime 合同。

## 唯一允许提前的实现

P0-03 只在 `packages/domain` 与 `packages/cognition-core` 增加 Task/attempt 和 Outcome 的最小纯类型、校验与转换及确定性测试。所有输入是合成内存值，时间、ID、revision 和证据由调用方显式传入。代码可以复用，但尚无生产调用方；不得从 apps、存储或 Runtime 接线。

其技术依赖仅是已接受的领域/运行/认知合同和现有 TypeScript 工具链，无文件/网络/进程/模型/数据库能力。`depends: []` 仅表达这个准备任务的技术独立性，不代表 P0 已完成、P1 可以启动或受限实验可以被重跑/替代。

任务状态计算与持久化事务必须区分：内存 CAS 不证明并发 writer 安全；注入的证据不是实际采集；pause/cancel 的规则不证明运行体已停止；Outcome 归约不证明真实 Artifact 合格。不得用通用布尔“已授权/已验证”参数宣称接入验证完成。

## 保持不变的门

- P0-01 原 D-04/D-08 实验、有限登记、独立接受与 G-2 验收全部保持；本任务不运行受限实验，也不转移执行环境绕过拒绝。
- P0-02 仍直接依赖 P0-01，原 G-5/恢复/规模合同保持。
- P1-01 同时依赖 P0-02 与 P0-03；其整体认知、Scope、协议和验收范围不因组件存在而完成。P1 及以后仍必须经过全部 P0 任务。
- P0-03 不认证 Z03/Z16 端到端，相关完整场景仍由原 P1 任务完成；P1-07 负责真实验证、Episode 与结果提交。
- 当前阶段仍是 P0。真实数据、运行入口、模型调用、存储迁移、外部副作用与正式发布均按原任务 gate 进入。
- 既有 checker、Workflow、风险等级、最终 HEAD 独立审查与受保护合入不变。准备任务不得用本规划为自身降低验证标准。

## 验证与回滚

规划以未修改的 design-plan checker 验证完整阶段依赖、无环性与负例，按根规则执行完整 check。确认原 P0-01/P0-02 任务对象、历史 work-packages、checker 和 Workflow 字节未变。实现任务另做纯规则正反例、输入不变及类型检查，再按 R2 或更高实际风险独立审查。

规划或纯组件均通过新 PR revert，不重写 main。后续若已被产品消费，先停止相关入口并核对依赖，再按对应恢复合同处理；不能仅删除计划条目掩盖实现事实。
