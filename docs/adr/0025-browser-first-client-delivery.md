# ADR 0025：先验收双端浏览器，再交付基础客户端

- 状态：Accepted（设计c98ba76c0349ca7afa44b1709cf5938437667d7e获[独立R3批准](https://github.com/ntygod/zhiwei-next/pull/128#issuecomment-6136080370)；最终实现HEAD另审）
- 日期：2026-10-13
- 工作项：#127；P1-08
- 被取代关系：补充 ADR0016/0024 的交付拆分；完整桌面系统集成仍归 P4，不改变认知、Runtime 或真实启用许可

## 背景

所有者要求按「解决 CI 阻塞 → 完成 PC 和安卓浏览器验收 → 客户端打包」继续推进，并明确安卓首版连接 PC 上的 Agent。原计划在 P1 提供浏览器工作台、P4 才交付完整 Windows 壳，移动审批是后期条件任务，缺少当前所需的基础安装交付。

PR128 的共享页面与受保护 API 已有开发证据，完整 CI 仍因原作业时限中止；实际浏览器与安卓设备验收没有证据。不能把代码测试、手机布局、可安装包或真实产品启用混为同一完成状态。

## 决策

1. P1-08 保持一个用户结果，按三个顺序交付切片推进：先在当前 primary 解决 CI 并完成浏览器接线交付，再取得 PC/安卓浏览器实际证据，最后以独立 execution/primary 交付复用同一 UI 的基础 PC 安装包和安卓 APK。各切片不并行占用产品 WIP。
2. 基础客户端属于 P1-08 的交付方式；P4-05 继续负责完整桌面系统能力，包括托盘、通知、系统凭据与多开控制，P4-06 继续负责升级、备份与恢复。不提前实现自动学习、主动性、后台委托或同步。
3. PC Daemon 仍是数据与 Worker 的唯一协调者。安卓首版是访问 PC Agent 的客户端，不在手机复制认知数据库或运行 Pi；只保留已获准的临时视图，沿用正文期限、版本与未知写语义。
4. 当前 literal loopback 与同源授权不因安卓需求改变。USB 同端口转发只是开发连接。面向基础 APK 的连接、设备认证、撤权和失联处理须另作具体设计并经独立 R3 审查；本交付顺序决定不授权新增 LAN 监听、放宽 CORS 或共享 PC 凭据。
5. 当前 CI 修复保留原完整检查、测试发现、断言、超时门与受保护合入链。针对实际耗时定位最小问题；源代码或治理改动绑定新最终 HEAD 的完整检查和独立审查，不移用 c7cb6a3 的批准。
6. 产品验收与真实启用继续遵守原前置门，P1-09 在 P1-08 各交付切片之后。正常/空/加载/错误/权限/降级、Cookie/配对、断线恢复、键盘/触屏及 200% 的实际证据按平台分别记录；未运行不得记为通过，既有受限实验与具体拒绝不重演或换路绕过。

## 备选方案

- 继续把所有安装交付留到 P4：不满足所有者当前顺序，改为先交付基础客户端，保留完整系统集成阶段。
- 手机直接运行 Agent 或复制数据库：与所有者选择及当前运行时边界不符，不采用。
- 直接把响应式页面套壳视为安卓支持：没有连接、认证和平台证据，不构成完成。

## 后果、验证与回滚

任务内容与完成条件更新唯一目录 development-plan.json，并机械生成 implementation-plan.md；路线图、验收标准与交接引用该顺序。代码已实现、浏览器已验收、安装包可用与真实入口已启用分别留证，不改变已有质量门。

回滚通过新受审 revert 撤回新增交付拆分或基础壳，不删已产生的开发证据和用户数据；真实入口仍按原验收门关闭。当前决定没有 Schema 迁移、网络监听或外部副作用。
