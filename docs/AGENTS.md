# docs/AGENTS.md

适用范围：`docs/**`。本文件在根目录规则之上，约束产品、架构、规划、ADR、Harness 和设计稿。

## 文档分工

| 目录 | 回答的问题 | 权威性 |
|---|---|---|
| `product/` | 产品为何存在、为谁服务、用户体验是什么 | 产品方向事实源 |
| `architecture/` | 目标系统如何分层、领域语义和安全边界是什么 | 目标架构事实源 |
| `adr/` | 为什么选择或放弃某项长期决策 | 已接受决策的最高事实源 |
| `planning/` | 当前做什么、按什么顺序、如何验收 | 当前范围事实源 |
| `harness/` | AI 如何选工作、验证、审查、合并和延续上下文 | 自主开发治理事实源 |
| `design/prototype/` | 页面和流程如何交流 | 说明性样例，不是业务事实源 |

代码和测试描述“当前已实现”，架构文档描述“目标结构”。两者未对齐时必须明确标注现状、目标和过渡阶段，不能把计划写成已实现。

## 按变更更新

- 产品承诺、目标用户或非目标变化：更新 `product/`，必要时新增 ADR。
- 模块边界、进程职责、数据真源或技术选型变化：更新 `architecture/` 和 ADR。
- 当前里程碑范围、顺序或完成定义变化：更新对应 `planning/` 文档。
- 自主权限、工作选择、风险门禁、独立审查或自动合并变化：更新 `harness/`、`harness.config.json` 和机器检查。
- 领域对象、作用域或生命周期语义变化：更新 `architecture/domain-model.md`。
- Pi 事件、嵌入方式或 Runtime 责任变化：更新 `architecture/pi-integration.md`。
- 权限、隐私、数据发送或自主等级变化：更新 `architecture/trust-and-safety.md`。
- UI 结构和交互原则变化：更新 `product/ui-design.md`；原型只负责演示。

不要为了“同步”而把同一段规则复制到多个文件。保留一个事实源，其余位置使用链接和简短摘要。

## ADR 规则

新 ADR 至少包含：状态、背景、决策、备选方案、后果和被取代关系。

- 已接受 ADR 不做语义重写；修正错字可以直接修改。
- 决策变化时新增 ADR，并将旧 ADR 标为 `Superseded`。
- ADR 记录决策，不承担实施计划和任务列表。
- 未验证的 Spike 结论应标为 `Proposed`，不能伪装成长期决策。

## 写作规则

- 叙述以中文为主，代码标识、协议字段和正式类型保留英文。
- 首次出现的核心术语给出清晰定义，之后保持同名，不随意创造近义词。
- 区分 `当前已实现`、`当前里程碑`、`最终蓝图`。
- 规划中的能力必须标注里程碑或状态；不要使用没有时间边界的“已支持”。
- 关键约束优先使用表格、状态机或短示例，避免长篇口号。
- 示例不得包含真实用户记忆、凭证、私有路径或可识别数据。
- 外部事实、版本和能力声明必须可验证；不确定时写明假设。
- 原型中的示例数据必须明确是演示内容，不能被当成产品指标或真实状态。
- Harness 文档必须区分机器可执行门禁与尚需后续实现的治理意图。

## 验证

- 检查相对链接、文件名、里程碑名称和术语是否一致。
- 文档描述代码行为时，核对当前实现或测试；不能只依赖旧文档。
- Harness 变化运行 `npm run check:agents` 和 `npm run check:harness`。
- 即使仅修改文档，也运行根目录要求的 `npm run check`，并报告无法运行的检查。
